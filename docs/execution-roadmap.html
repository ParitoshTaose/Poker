02 Strategy

One base, three forks — don't marry the churn model yet

The smartest thing this project can do is delay one decision: which supervised question becomes the headline. Build one shared base, prototype three candidate questions on it cheaply, and let the data pick the winner.

The base is everything the forks share: the Bronze → Silver → Gold pipeline (Steps 1–4) and the K-Means player segmentation from the original plan. The base is never at risk — every fork needs it, so no work on it can be wasted. On top of the base sit three forks, each a different supervised question asked of the same Gold tables:

  • Fork A — Churn classification. "Which currently-active players will stop playing?" The original headline. Label: a player active in the first stretch of the 23 days who disappears in the final week — honestly called short-horizon lapse, not churn.
  • Fork B — Player value prediction. "How much is each player worth to the operator next week?" A regression on future volume / rake contribution. Retention budgets only make sense when you know who is worth retaining.
  • Fork C — Hand-economics prediction. "How big will the pot be, given the table?" A regression at the hand level, not the player level: predict pot size (in big blinds) from table composition, stake and time. Pot size × rake % = revenue per hand — this is a revenue-per-seat forecasting tool.
The fork strategy. The base is built once and shared. The three candidate questions are prototyped cheaply on the subset in Step 5, and only the winner is carried into the expensive phases. The losers don't vanish — they become the report's "alternatives considered" paragraph.
Key idea — two levels of comparison, and where the "≥ 2 approaches" rule is met The brief demands at least two ML approaches with compared metrics. That requirement is satisfied inside the winning fork — two different MLlib algorithms trained on the same question and scored against each other (Step 8) — plus K-Means segmentation as the unsupervised layer. The fork-level bake-off is a bonus on top: it shows the panel you chose your question deliberately, which is exactly what "justify every decision" means.
Where it breaks — the forks are not on a level playing field Money-based targets (Fork B's rake/winnings, part of Fork A's value features) only reconcile on ~⅓ of hands — 211 of 991 sampled hands lack a winnings column and 486 more have it all-zero, for reasons still unexplained. Behavioural features work on ~100% of hands, and pot size is computable from the betting actions themselves on essentially every hand. The bake-off must therefore compare coverage, not just accuracy — a slightly better model on a third of the data can be the worse choice.

Line by line — what each command actually does, and why it's there:

python3.13 -m venv .venv
Creates a private, disposable copy of Python just for this project, living in a folder called .venv. Anything you pip install next goes in there, not into your Mac's system Python — so it can't clash with anything else, and you can delete the folder and start clean if it ever gets messy.
source .venv/bin/activate
Switches your terminal into that private copy. Until this runs, typing python or pip quietly uses the Mac's built-in Python 3.9.6 — the one with no tomllib, which is exactly what breaks the parser if you forget this step.
pip install pyspark polars
pyarrow pandas
Installs the four libraries the whole pipeline depends on: PySpark (the Python interface to Spark, the distributed engine used from Step 4 onward), Polars (the fast dataframe library from the Session 3/7/8 labs, doing the heavy lifting in Steps 2–3), PyArrow (the shared in-memory format Parquet and Spark both speak, so data moves between them without being copied or re-encoded), and Pandas (some Spark and reporting tooling still expects it as glue).
export JAVA_HOME=$(/usr/libexec/
java_home -v 17)
Spark itself is written in Scala and actually runs on the Java Virtual Machine — PySpark is a thin Python wrapper around it. A Mac can have several Java versions installed at once; this line tells your terminal exactly which one (17, already installed) Spark should launch against.
SparkSession.builder
.master('local[*]')...
This line actually starts a tiny Spark cluster — just one, running entirely inside your laptop, using every CPU core (local[*]). It then asks that cluster to count 1,000 numbers. Printing spark ok: 1000 proves the full chain works: Spark can launch, hand out work, and return an answer — the exact machinery Step 4 leans on for real.
Key idea — if the smoke test complains about the Python version PySpark is sometimes slow to support the newest Python. If step 4 fails with a version error, install a slightly older one and rebuild the venv: brew install python@3.12 then python3.12 -m venv .venv. Everything else on this page is unchanged — tomllib works on any Python 3.11+.

Downloads the repository's structure and history but not the file contents — you get the full folder tree instantly, with the actual data fetched only when asked for. Without this flag git would pull every file in the repo, including the 619 M bot-vs-bot hands this project deliberately ignores.
--sparse
Starts the working copy almost empty instead of checking out everything, so you can name the one folder you want in the next command. The two flags work as a pair: --filter controls what gets downloaded, --sparse controls what gets written to disk.
git sparse-checkout set
data/handhq
This is the line that does the actual downloading. It says "materialise only data/handhq" — the real-money human hands — and git then fetches exactly those blobs. Everything else in the repo stays as a name in the index, costing nothing.

05 Step 2

Prove the parser — on all six venues, not one

The parser already exists and is tested — on PokerStars files only. Before anything is built on top of it, run it against one file from each of the six platforms.

First — what the parser actually does

A .phhs file is not a spreadsheet. It is a stack of nested records, one per hand, each holding lists of players, lists of money, and a list of actions written in shorthand. Nothing in that shape can be put in a table, let alone fed to a model. The parser's entire job is to flatten one awkward nested hand into three flat tables, each at a different grain — the word for "what one row means".

TableOne row = What it is for
handsone hand of poker The hand's facts: venue, stake, time, pot size, rake, whether a flop came, whether anyone showed cards. Fork C (pot-size prediction) trains on this table.
hand_playersone player in one hand Roughly 6 rows per hand. Position, money invested, money won, and the behaviour flags — vpip, pfr, folded. Grouping this by player is what produces the player features for segmentation and churn.
actionsone decision by one player Roughly 10.6 rows per hand — the most granular level. Every fold, check, call, bet, raise, in order, with amounts. This is the ~229 M-row table that makes the project genuinely "big data".

Three lines of parse_phh.py carry almost all the difficulty. They are worth understanding, because each one is a decision you will have to defend:

raw = tomllib.load(f)
The single biggest shortcut in the project. The .phhs format turns out to be valid TOML, a standard config format Python has read natively since version 3.11. So there is no hand-written parser — one standard-library call turns the whole file into typed Python objects, with time arriving as a real time object rather than text. This is why the venv must be Python 3.11+ — the Mac's built-in 3.9.6 has no tomllib and the script dies immediately.
elif verb == "cc": target = max(street_bet) amount = target - street_bet[idx] if amount > 0: # CALL else: # CHECK
The correctness test made of code. The format writes cc for both "check" and "call" — two very different acts stored identically. The fix: look at the biggest bet on the street and subtract what this player has already put in. If money would have to move, it was a call; if not, it was a free check. Get this wrong and the big blind — who can always check for free — looks like they voluntarily played every single hand, inflating every downstream statistic.
s = sorted(committed, reverse=True) uncalled = s[0] - s[1] pot = sum(committed) - uncalled rake = pot - sum(winnings)
How rake is recovered when nobody recorded it. The dataset never stores the operator's cut, so it is derived: the pot is everything players put in, minus the uncalled portion of the last bet — if you bet $10 and everyone folds, $10 comes back to you and was never really in the pot. Subtract what players collected from what was in the pot, and the difference is the house's take. Omit the uncalled-bet correction and the answer is a nonsensical ~40% rake. With it: exactly $0.00 on hands that end before the flop.

Line by line — what the parser is telling you:

hands=989 hand_players=6098 actions=10440
The three tables were built, and here is how many rows each got. One file produced 989 hands, 6,098 player-seats and 10,440 individual decisions. These are the same three grains described above — this line is proof the flattening worked.
actions per hand = 10.56 players per hand = 6.17
Sanity checks, and the project's scale argument. 6.17 players per hand is exactly right for 6-max tables. The 10.56 is the number that justifies the whole exercise: ×21.6 M hands ⇒ ~229 M action rows, about 218× what Excel can hold. This single figure is the honest answer to "why is this a Big Data project?"
action mix: fold 4874, check 1849, call 1531, bet 791, raise 769, show 626
A tally of what players did. Folding is ~47% of all actions — correct, and important: good poker is mostly not playing. Note check and call appear as separate counts even though the file stores both as cc — visible proof the disambiguation logic ran. Only 626 shows against 989 hands is the 22.4% showdown rate: most hole cards are never revealed.
reconciled rake on 288 hands (preflop-only 109, flop 179)
The honest limitation. Rake could only be computed for 288 of 989 hands — the rest are missing winnings or have it recorded as all zeros. This is the "money coverage is ~⅓" problem: behavioural features work on 100% of hands, money features do not. It belongs in the report, not hidden.
preflop rake values: [0.0]
The most satisfying line in the output. Every one of the 109 hands that ended before the flop was raked exactly $0.00 — no exceptions, no rounding noise. That is the poker industry's "no flop, no drop" rule, recovered from raw data by arithmetic alone. It is strong evidence the pot maths is right, because a bug would produce scattered near-zero values instead of a clean single number.
flop rake median = 0.05 median % = 3.70%
Once a flop is dealt, the house takes a median of $0.05 per hand, about 3.7% of the pot — consistent with a real ~5%-capped rake structure. This is the revenue model of the entire business, reconstructed from a column that was never recorded. It is what lets the project talk about operator revenue at all.
pooled VPIP = 27.9% pooled PFR = 10.2%
The two standard poker behaviour stats, across all players mixed together. VPIP = how often a player voluntarily puts money in — think "engagement rate". PFR = how often they raise first — think "aggression". 27.9 / 10.2 is a believable low-stakes average. "Pooled" means it is not yet per player — turning this into one row per player is exactly what Step 4 does, and those per-player numbers are what the clustering consumes.
big blinds who 'vpip'd = 27.4%
THE correctness test — and it passed. The big blind has already been forced to post money, so if nobody raises they see the flop for free. That free check is stored identically to a real call. Had the parser confused them, this number would read ~100% and every player would look far looser than they are. 27.4% ≈ the pooled 27.9% is the signal that the check/call logic is sound — and therefore that everything built on top of it is trustworthy. Read this line on every venue, every time.
Where it breaks — the one number that must be right Big-blind VPIP must land near ~27%, never near 100%. The big blind can check for free pre-flop, which looks identical to a call in the action codes. Count that wrong and every player's VPIP inflates, and the clustering downstream becomes meaningless. parse_phh.py prints this check on every run — read it every time, on every venue.
Key idea — dropped hands are reported, never silent A small number of hands per file are legitimately dropped (no big blind ⇒ money cannot be normalised) — 2 in the PokerStars sample, 8 in a Full Tilt one. Fine — but count them and write the count down. "We dropped 0.2% of hands, here is why" is a sentence that earns marks; silent data loss is what "justify every decision" is designed to catch. The parser now prints a dropped hands: line on every run, broken down by reason, and build_silver.py totals it across all 21,782 files.
Where it breaks — Step 2 as written is NOT strong enough. Proven on 6 Aug 2026. Testing one file per venue passed cleanly on all six — and the full Step 3 run then crashed anyway, twice, because these defects hide in files that a one-file sample never touches. All were found only by running all 21,782 files:
  • Ongame writes string hand IDs. Every other venue uses integers; ONG uses 'R5-2483622-63'. Polars inferred a number column from the first venues and threw a fatal error the moment ONG's files were reached — 8,712 files in, roughly 15 minutes of work lost.
  • A few hands carry no hand id at all. The parser assumed the field always exists, so a single malformed hand raised an error that discarded the entire file — 31 Full Tilt files, ~31,000 good hands, thrown away to protect 31 bad ones.
  • The same field is an integer in one hand and a decimal in the next. TOML infers types from how a value is written: 25 loads as a whole number, 25.0 as a decimal. Audited across all six venues, five money fields — starting_stacks, winnings, blinds_or_straddles, antes, min_bet — mix both types inside a single list. Polars guesses a column's type from the first rows it sees, so it guessed "whole number", then died when a decimal arrived. This killed the run twice, at the same point, with two different error messages.
  • Hand IDs are assigned per venue, so uniqueness across venues is not guaranteed. Absolute (3.02–3.09 bn) and iPoker (3.41–3.49 bn) number in the same order of magnitude. Measured honestly: a 240-file sample across all six venues found zero actual collisions, and those two observed ranges do not overlap — so this is a latent risk, not an observed bug. It is listed here because it is the only one of the three that would produce no error at all, and a silent bad join is far more expensive than a crash.
Fixed: hand IDs are forced to text, hands missing an id are dropped individually and counted, and every table now carries hand_uid = "{site}:{hand_id}" — join on that, never on hand_id. The PokerStars numbers above re-ran identical afterwards (989 hands · VPIP 27.9% · BB-VPIP 27.4%), which is how you know a fix didn't quietly change the results. Always re-run a known-good case after fixing a parser.
Key idea — stop guessing schemas; declare them The first two failures were each patched individually, and the run died again at exactly the same batch with a different message. The real fix was to stop treating them as separate bugs: every value is now coerced to one fixed type as it leaves the parser, and build_silver.py declares an explicit schema for all three tables instead of letting Polars infer one from a sample. Why this is the right fix, in one sentence for the report: inference is a guess made from the first few rows, so it fails late, randomly, and only at scale — a declared schema fails immediately and in the same place every time. Same principle as a database column type. Pre-flight check added: all 27 venue/stake partitions are validated against the schema before the long run starts — seconds, instead of discovering it 15 minutes in.
Takeaway — this is the most valuable paragraph in your report Do not hide this. "Our validation step passed, the full run still failed twice — here is what one-file-per-venue could not see, and here is how we changed the test" is exactly the engineering judgement the Data Engineering & Architecture mark rewards. A pipeline that never hit a problem usually means nobody looked. Bronze → Silver: every file, three Parquet tables

Now the parser runs over every Bronze file and writes the three flat tables — hands, hand_players, actions — as Parquet into data/silver/. Plain Python and Polars; Spark is not needed yet.

Where it breaks — the version in the guides would have run this Mac out of memory Earlier drafts of this page (and the pipeline guide, step 4) show a simpler script that parses every file first and writes at the very end. That was written assuming a ~1.7 GB subset. Bronze actually holds 21,782 files (see Step 1's correction), and the simple version keeps every parsed row in RAM until the last one is done. Measured, not guessed: parsing just 200 files peaked at 1.08 GB of RAM and produced 2.17 M action rows. Scaled to 21,782 files that is on the order of 100+ GB — on a 16 GB machine. The run would have swapped, crawled, and died, quite possibly after an hour of apparently-fine progress. The fix is batching, below.
src/build_silver.py — batched, 8 coresstep 3 · the version that runs
from multiprocessing import Pool
from pathlib import Path
import polars as pl
from parse_phh import parse_file

SRC = Path("data/bronze/handhq")
OUT = Path("data/silver")
BATCH = 500          # keeps peak RAM to a few GB, whatever the file count

TABLES = ["hands", "hand_players", "actions"]

def safe(p):
    try:
        return parse_file(p)
    except Exception as e:
        print("SKIP", p.name, e)   # never let one bad file kill the run
        return None

if __name__ == "__main__":
    files = sorted(SRC.rglob("*.phhs"))
    print(len(files), "files")
    for name in TABLES:
        (OUT / name).mkdir(parents=True, exist_ok=True)

    skipped = 0
    row_totals = {name: 0 for name in TABLES}

    with Pool(8) as pool:                      # 8 of the 10 cores
        for b in range(0, len(files), BATCH):
            batch = files[b:b + BATCH]
            results = pool.map(safe, batch, chunksize=8)
            skipped += sum(1 for r in results if r is None)
            ok = [r for r in results if r is not None]
            for i, name in enumerate(TABLES):
                rows = [row for res in ok for row in res[i]]
                if rows:
                    part = b // BATCH
                    pl.DataFrame(rows).write_parquet(
                        OUT / name / f"part-{part:04d}.parquet")
                row_totals[name] += len(rows)
            print(f"batch {b // BATCH}: {b + len(batch)}/{len(files)} files", flush=True)

    print("SKIP count:", skipped)
    for name in TABLES:
        print(name, row_totals[name], "rows")

Line by line — the four ideas that make this work:

with Pool(8) as pool: pool.map(safe, batch)
Use 8 of the Mac's 10 cores at once. Pool starts 8 independent Python processes and map deals files out to whichever is free. This is legitimate parallel computing — and it is the same idea as MapReduce from Sessions 1–4, just on one machine instead of a cluster. Parsing is embarrassingly parallel: no file needs to know anything about any other, so there is nothing to coordinate. Two cores are left for macOS so the laptop stays usable.
for b in range(0, len(files), BATCH): batch = files[b:b + BATCH]
The memory fix. Instead of "parse all 21,782, then write", this does "parse 500, write them, forget them, repeat". Peak memory is set by the batch size, not the dataset size — so the same script would work on ten times the data without changes. This is the single most important line in the file.
except Exception as e: print("SKIP", p.name, e) return None
One corrupt file must not kill a 20-minute run. If a file fails, say so, return nothing, carry on. Returning None (rather than empty lists) lets the failures be counted — skipped is printed at the end. The rubric's "justify every decision" line is really asking whether you noticed your losses.
OUT / name / f"part-{part:04d}.parquet"
Each batch writes its own numbered file, so you end up with data/silver/actions/part-0000.parquet, part-0001.parquet… Polars and Spark both read a folder of parts exactly as if it were one table, so nothing downstream has to care. This is precisely how real distributed systems store data — many parts, read in parallel — and it is the same partitioning idea already used for Bronze.

Takeaway — why Parquet is the architecture argument Raw text becomes far smaller Parquet because Parquet is columnar and compressed — a query that needs three columns reads three columns, not every byte. Text files force you to read every character of every row just to count something. One trap this table hands to Step 5

The 100-hand threshold is on hands played, not on hands where the money is usable — and those are very different numbers. Median money_hands is 92, and only 88,655 of the 106,977 players have any usable money at all. So the win-rate column has a wild tail: median bb_per_100 is a sensible −5.3 (that is rake drag, exactly as it should be), but 6.4% of players sit beyond ±200 — and every one of those is a small sample, not a superstar. The worst case is a player with 103 hands played but only 7 with usable money, whose −1,494 bb/100 is computed off those 7 hands. Fork B must therefore filter on money_hands, never on hands_played. Gold deliberately stores the raw value and both counts rather than clipping — winsorising here would hide the problem instead of letting Phase 2 decide it, and "handle your outliers" is a named part of that mark.

Where it breaks — putting Spark's scratch in /tmp killed two full runs A shuffle is Spark moving rows between cores so that every row for one player ends up in the same place. It does not do that in memory — it writes many GB to disk, at spark.local.dir, then reads it back. Point that at /tmp and anything that tidies /tmp while the job runs — macOS's own cleaner, a sandbox, a CI agent — deletes the job's working data out from under it. It then dies about ten minutes in with java.io.FileNotFoundException: /private/tmp/spark-scratch/blockmgr-…/shuffle_16_1472_0.data, which looks like a Spark bug and is not one. The tell: it always dies on a shuffle read, never on a write — the file was written fine, then vanished. Fix: keep scratch on the project disk (data/_work/spark-scratch, gitignored). This run spilled 1.4 GB within the first minute, so it is not a theoretical concern. Check free space before a full run: df -h .
Where it breaks — Step 4's sanity check found a bug in Step 3, and it cost a full rebuild The first Gold table looked perfect until the last line of the run: every high-volume player had a win rate of about −100 bb/100 — losing a full big blind every single hand. In a game where the house takes only rake, that is impossible, so the data was wrong. The cause was in parse_phh.py, not in Spark. If you bet $50 and everyone folds, that $50 never entered the pot and comes straight back to you. The parser correctly removed it from the pot — which is exactly why rake reconciled to the penny and nobody noticed — but never removed it from that player's own invested. Players were charged for chips they got back, on 99.4% of hands, by a mean of 7.35 bb — 17× the rake itself. The test that catches it is one line of arithmetic. Poker is zero-sum apart from the rake, so across every seat of a hand sum(net_bb) == −rake_bb. Before the fix the shortfall was exactly the uncalled bet: the identity sum(net_bb) + uncalled_bb + rake_bb = 0 held on 100% of 852,293 reconciled hands — proof, not suspicion. After the fix, 5,378,874 / 5,378,874 hands satisfy the real identity. Both checks now run automatically, in the parser's self-test and in Step 4's sanity block. The sentence worth putting in the report: a downstream check found an upstream bug that every upstream check had passed. Rake reconciled perfectly and the data was still wrong. Silver was rebuilt from all 21,782 files (27 min) and came back with byte-identical row counts and an identical hands table across all 21,556,288 non-duplicate hands — which is how you prove only the intended columns moved.
Where it breaks — "winnings recorded" is not "winnings usable", and the gap is a venue property The obvious money filter — "did every seat report a figure, and did the pot pay out?" — is wrong. 13.8% of hands pass it while their winnings sum to ~1.5× the pot, and averaging those in is the second reason everyone looked like a loser. The right filter is the parser's own reconciliation: rake_bb IS NOT NULL.

Where it breaks — the showpiece feature silently reads "1" on a venue that records no tables at all The multi-tabling detector is the feature that separates a human from a professional without any labelled data: one person plays one table; a grinder plays a dozen. Distinct table ids per venue, measured: PS 11,355 · ONG 1,252 · ABS 1,046 · FTP 809 · PTY 697 · IPN 1. iPoker writes the literal string "HandHQ" — the name of the company that packaged the data — into all 5,996,194 of its table fields. So every iPoker player scores exactly max_tables = 1. That is not a measurement of single-tabling; it is a missing value wearing a plausible number, and it is far more dangerous than a blank, because nothing downstream can tell the difference. Left alone, K-Means would file all 15,549 iPoker players — 14.5% of the Gold table — as recreational single-tablers, which is exactly backwards for the grinders among them, and those grinders are the whole point of the ecosystem thesis. Fix: null max_tables, avg_tables and distinct_tables for any venue with ≤1 distinct table id, and carry tables_recorded so the absence is explicit. A null a model can see beats a number that lies to it.
Where it breaks — the six venues stop recording on different days, so "churn" can be an illusion Every source folder is labelled 2009-07-01_2009-07-23, but the hands' own timestamps run to day 26, and each venue ends somewhere different: ABS 20 · PS 20 · FTP 23 · ONG 24 · IPN 26 · PTY 26. So a single global rule — "played in the final week?" — would mark every Absolute and PokerStars player as lapsed by construction: 9.55 M hands, 44% of the dataset, labelled churned because the recording stopped, not because anyone left. A churn model trained on that learns to predict which site a player used. The fix is one decision, and it is worth a rubric mark: every activity window is measured backwards from that venue's own last observed day, via site_last_day and days_since_last. Gold carries the raw material; Step 5 picks the cut-point knowing this.

Phase 3 — the models, in MLlib, metrics compared

  • K-Means segmentation (the base, always in): choose k with an elbow/silhouette check and business readability — four clusters nobody can name lose to three clusters management can act on. Compare the found clusters against the four hypothesised archetypes; matching or not matching are both findings.
  • Winning fork, algorithm 1 — a linear baseline. Logistic regression (Fork A) or linear regression (B/C). Interpretable coefficients: "what drives the risk" is a slide.
  • Winning fork, algorithm 2 — a tree ensemble. Random forest or gradient-boosted trees. Usually stronger, less interpretable — which is exactly the comparison story.
  • The comparison table: AUC / precision / recall at a chosen operating point for classification; RMSE / MAE and error-vs-baseline for regression — plus one row for the dumb baseline, so every gain is visible and honest.
Where it breaks — leakage, the silent metric-inflator Split so the test set is information the model could not have seen. For the player-grain forks: features from days 1–16, labels from days 17–23, and split by player — no player appears in both train and test. For the hand-grain fork: split by time — train on the early days, test on the late ones. A random shuffle would leak the same player (or the same session) across the split and quietly flatter every metric.
Takeaway — tie one metric to money The Model Evaluation marks are earned the moment a threshold becomes a business decision: "at this cut-off, the retention team contacts the top N% of at-risk players; a false positive costs one bonus offer, a false negative costs a customer's remaining lifetime value." One sentence like that turns a metrics table into a management tool — which is the course's whole thesis.
