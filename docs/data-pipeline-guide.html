01 Reality check

What "20 GB" actually means here

The single most useful thing to understand up front: the data shrinks dramatically as it moves through your pipeline. Only the first stage is big.

Bars to scale. Machine learning never touches the big data. By Phase 3 you are working with something smaller than a photo library.
Key idea — you have a disk problem, not a memory problem With 272 GB free, disk is comfortable as long as you extract selectively. The 20.29 GB zip is compressed; extracting all of it would produce something on the order of 100 GB, almost all of it bot hands with no business meaning. Extract only data/handhq/.
Takeaway — and this changes your whole plan The GitHub copy of the dataset is only 1.71 GB (we checked the API). It is a subset, not the full 21.6 million hands — but it is more than enough to build, debug and demo the entire pipeline. Start there. Only reach for the 20 GB Zenodo archive at the very end, when you want the headline numbers.
02 Concepts

Spark, built from three things you already know

You have already met every idea in Spark. They were just wearing different clothes. Here they are, mapped one to one onto your own course notes.

You are not learning a new paradigm. You are learning new vocabulary for three things your course already taught you.
Takeaway The one genuinely new idea is that Spark does all this across many machines at once, and survives one of them dying — which is precisely the fault-tolerance story from your Session 1 HDFS note. On your laptop, "many machines" just means your 10 cores.
03 Concepts

The five words you need

WordWhat it means, plainly
PartitionA chunk of your rows. Spark splits the data into partitions and gives each one to a core. 10 cores means about 10 chunks being worked on at once. Same concept as an HDFS block.
TransformationAn instruction like "filter these rows" or "add this column". It does not run. Spark just writes it down. Exactly like building a Polars lazy query.
ActionA command that forces everything to actually execute — .show(), .count(), .write(). Polars' .collect().
ShuffleThe expensive one. When Spark must move rows between partitions so that all rows for the same player end up together. Grouping by player means shuffling everything. This is where your 16 GB gets used.
Driver / executorThe driver is the boss process holding your plan; executors are the workers. On a laptop they all live in one process — which is why pulling data back to the driver is so dangerous.
This is the one operation that makes the project genuinely "big data" — and the one that will make your laptop's fans spin.

These files are valid TOML. TOML is a standard configuration format, and Python has had a reader for it built into the standard library since version 3.11. So you do not need to write a text parser at all:

pythonthis genuinely works
import tomllib

with open(path, "rb") as f:      # note: binary mode, tomllib requires it
    hands = tomllib.load(f)

print(hands["1"]["time"])        # datetime.time(0, 0) - already a real time object

Each hand comes back as a dictionary with properly typed fields — numbers as numbers, the timestamp as a datetime.time. No regular expressions. No string slicing. No edge cases.

07 Step 3

The parser — tested, and yours to use

This is the heart of the project. It turns one file of raw hands into three flat tables. Every line below has been run against real data.

The tricky part is not reading the file — TOML does that. The tricky part is replaying the betting, so you can tell a check from a call, work out what each player put in, and know when a new betting round starts. Here is the logic in plain English before the code:

  1. Start the pot with the forced blinds. Mark them as not voluntary.
  2. Walk the action list in order. A d db line means a new street began — reset the per-street bet tracking.
  3. For cbr, the number is the player's new total for that street, so the money added is that total minus what they already had in.
  4. For cc, compare the highest bet on the street to what the player has in. If the difference is zero it was a check; if positive it was a call — and only a call counts as voluntary.
  5. At the end, give back the uncalled part of the final bet before computing the pot. Skipping this is what produced a nonsensical 40% rake on our first attempt.
parse_phh.pytested · 989 hands parsed
"""Parse PHH (.phhs) poker hand-history files into flat tables."""
import tomllib
from pathlib import Path

STREETS = ["preflop", "flop", "turn", "river"]


def parse_file(path):
    """Return (hands, hand_players, actions) as lists of dicts."""
    path = Path(path)
    venue_dir = path.parent.parent.name    # PS-2009-07-01_..._25NLH_OBFU
    stake     = path.parent.name           # 0.25
    with open(path, "rb") as f:
        raw = tomllib.load(f)

    hands, hand_players, actions = [], [], []

    for local_id, h in raw.items():
        players = h["players"]
        n       = len(players)
        blinds  = h.get("blinds_or_straddles", [])
        bb      = blinds[1] if len(blinds) > 1 else None
        if not bb:
            continue                       # no big blind = cannot normalise money

        committed  = [0.0] * n              # total put in, whole hand
        street_bet = [0.0] * n              # put in on THIS street
        vol        = [False] * n            # did they CHOOSE to invest?
        raised_pf  = [False] * n
        n_bets     = [0] * n                # postflop bets/raises
        n_calls    = [0] * n                # postflop calls
        showed     = [False] * n
        folded     = [False] * n

        for i, a in enumerate(h.get("antes", [])):
            if i < n: committed[i] += a
        for i, b in enumerate(blinds):       # forced money: NOT voluntary
            if i < n:
                committed[i] += b
                street_bet[i] = b

        street = 0
        order  = 0
        for act in h["actions"]:
            parts = act.split()
            if parts[0] == "d":                # dealer, not a player
                if parts[1] == "db":            # board dealt -> new street
                    street += 1
                    street_bet = [0.0] * n
                continue

            idx    = int(parts[0][1:]) - 1
            verb   = parts[1]
            amount = 0.0
            kind   = verb

            if verb == "cbr":                # bet/raise TO a street total
                target = float(parts[2])
                amount = target - street_bet[idx]
                committed[idx] += amount
                street_bet[idx] = target
                vol[idx] = True
                kind = "bet" if sum(1 for x in street_bet if x > 0) <= 1 else "raise"
                if street == 0: raised_pf[idx] = True
                else:            n_bets[idx] += 1

            elif verb == "cc":                 # CHECK or CALL - disambiguate!
                target = max(street_bet)
                amount = target - street_bet[idx]
                if amount > 0:               # money moved => it was a CALL
                    committed[idx] += amount
                    street_bet[idx] = target
                    vol[idx] = True
                    kind = "call"
                    if street > 0: n_calls[idx] += 1
                else:                          # free => it was a CHECK
                    kind = "check"

            elif verb == "f":
                kind = "fold"; folded[idx] = True
            elif verb == "sm":
                kind = "show"; showed[idx] = True

            order += 1
            actions.append({
                "hand_id": h["hand"], "player_id": players[idx],
                "street": STREETS[min(street, 3)], "action": kind,
                "amount": round(amount, 4), "amount_bb": round(amount / bb, 4),
                "action_order": order,
            })

        # the uncalled part of the last bet goes back to its owner
        s        = sorted(committed, reverse=True)
        uncalled = (s[0] - s[1]) if n > 1 else 0.0
        pot      = sum(committed) - uncalled

        w, rake = h.get("winnings"), None
        if w and sum(w) > 0:
            r = round(pot - sum(w), 4)
            if -0.005 <= r <= max(pot * 0.15, 0.02):   # sanity gate
                rake = max(r, 0.0)

        hands.append({
            "hand_id": h["hand"], "venue": h.get("venue"), "venue_dir": venue_dir,
            "stake": stake, "big_blind": bb, "table_id": h.get("table"),
            "year": h.get("year"), "month": h.get("month"), "day": h.get("day"),
            "time": str(h.get("time")), "n_players": n,
            "seat_count": h.get("seat_count") or n,
            "saw_flop": street >= 1, "showdown": any(showed),
            "pot": round(pot, 4), "pot_bb": round(pot / bb, 4),
            "rake": rake,
            "rake_bb": round(rake / bb, 4) if rake is not None else None,
        })

        for i, pid in enumerate(players):
            won = w[i] if w and i < len(w) else None
            hand_players.append({
                "hand_id": h["hand"], "player_id": pid,
                "position_idx": i + 1,          # p1=SB, p2=BB, pN=button
                "is_sb": i == 0, "is_bb": i == 1, "is_button": i == n - 1,
                "starting_stack": h["starting_stacks"][i],
                "invested": round(committed[i], 4),
                "invested_bb": round(committed[i] / bb, 4),
                "winnings": won,
                "net_bb": round((won - committed[i]) / bb, 4) if won is not None else None,
                "vpip": vol[i], "pfr": raised_pf[i], "folded": folded[i],
                "showed": showed[i],
                "postflop_bets": n_bets[i], "postflop_calls": n_calls[i],
            })

    return hands, hand_players, actions

08 Step 4

One folder → Parquet

Before Spark, prove it works on a thousand files with plain Python. Your Mac has 10 cores; use them.

build_silver.pyplain Python, no Spark
from multiprocessing import Pool
from pathlib import Path
import polars as pl
from parse_phh import parse_file

SRC = Path("phh-dataset/data/handhq")
OUT = Path("silver"); OUT.mkdir(exist_ok=True)

def safe(p):
    try:
        return parse_file(p)
    except Exception as e:
        print("SKIP", p.name, e)      # never let one bad file kill the run
        return [], [], []

if __name__ == "__main__":
    files = sorted(SRC.rglob("*.phhs"))
    print(len(files), "files")

    with Pool(8) as pool:              # 8 of your 10 cores
        results = pool.map(safe, files, chunksize=8)

    for i, name in enumerate(["hands", "hand_players", "actions"]):
        rows = [r for res in results for r in res[i]]
        pl.DataFrame(rows).write_parquet(OUT / f"{name}.parquet")
        print(name, len(rows), "rows")
Key idea — why not Spark for this bit? Parsing files is embarrassingly parallel — a thousand files, none of which needs to know about any other. No shuffle, no coordination. Plain multiprocessing does it with less overhead and far less to go wrong. Bring Spark in when you need to group across the whole dataset, which is the next step. Your report should say exactly this. Choosing the simpler tool where it fits, and explaining why, reads as engineering judgement rather than tool-worship.
Superseded 6 Aug 2026 — the code above will NOT run as written. Use the roadmap's version. Two assumptions behind this snippet turned out to be false when it was actually executed:
  • There is no 1.71 GB subset. The GitHub route delivers 15 GB / 21,782 files — effectively the whole real-money dataset. Collecting all rows before writing needs on the order of 100+ GB of RAM on a 16 GB machine. Batch it.
  • Venues disagree on data types — Ongame writes string hand IDs where everyone else writes integers, which kills the Parquet write mid-run.
The working, measured version — batched, with per-reason drop counts and a hand_uid join key — is in the execution roadmap, Step 3, and on disk as src/build_silver.py. This block is kept only to show the simpler idea it grew from.
09 Step 5

Now bring in Spark

From here on you are working with Parquet, which Spark reads natively and fast.

features.pyPySpark
from pyspark.sql import SparkSession, functions as F, Window

spark = (SparkSession.builder
    .appName("quickstack-poker")
    .master("local[8]")                          # 8 of your 10 cores
    .config("spark.driver.memory", "9g")          # leave RAM for macOS
    .config("spark.sql.shuffle.partitions", "48") # default 200 is far too many locally
    .config("spark.local.dir", "/tmp/spark-scratch") # spill space on your fast SSD
    .getOrCreate())

hp      = spark.read.parquet("silver/hand_players.parquet")
hands   = spark.read.parquet("silver/hands.parquet")

# nothing has run yet - these are just instructions (lazy, exactly like Polars)
joined = hp.join(hands.select("hand_id", "venue", "day", "time",
                            "table_id", "saw_flop"), "hand_id")

joined.explain()          # see the plan WITHOUT running it - like Polars .explain()
print(joined.count())     # THIS is the action that finally executes everything
Takeaway If you have used Polars' lazy mode, you already know this feeling: you build up a query, call .explain() to inspect the plan, and only .count() or .write() makes it actually happen. Spark is the same idea, spread across cores instead of one process.
10 Step 6

Build the features — the real group-by

This is the Gold table. One row per player, and the moment the project becomes small again.

features.py — continuedthe shuffle happens here
# ---- the core behavioural features: one row per player ----
core = (joined
    .groupBy("venue", "player_id")
    .agg(
        F.count("*").alias("hands_played"),
        F.avg(F.col("vpip").cast("int")).alias("vpip"),
        F.avg(F.col("pfr").cast("int")).alias("pfr"),
        F.sum("postflop_bets").alias("bets"),
        F.sum("postflop_calls").alias("calls"),
        F.avg(F.col("showed").cast("int")).alias("wtsd"),
        F.avg("net_bb").alias("avg_net_bb"),      # null-safe: ignores missing
        F.countDistinct("day").alias("days_active"),
        F.countDistinct("table_id").alias("distinct_tables"),
    )
    .withColumn("vpip_pfr_gap", F.col("vpip") - F.col("pfr"))
    .withColumn("aggression_factor",
                F.col("bets") / F.greatest(F.col("calls"), F.lit(1)))
    .withColumn("bb_per_100", F.col("avg_net_bb") * 100)
)

# ---- the showpiece: how many tables at once? ----
# bucket every action into its minute, then count distinct tables per player-minute
multi = (joined
    .withColumn("minute", F.concat_ws(":", "day", F.substring("time", 1, 5)))
    .groupBy("venue", "player_id", "minute")
    .agg(F.countDistinct("table_id").alias("tables_this_minute"))
    .groupBy("venue", "player_id")
    .agg(F.max("tables_this_minute").alias("max_tables"),
         F.avg("tables_this_minute").alias("avg_tables"))
)

gold = (core.join(multi, ["venue", "player_id"], "left")
            .filter(F.col("hands_played") >= 100))   # minimum-hands threshold

gold.write.mode("overwrite").parquet("gold/player_features.parquet")
print("players in gold table:", gold.count())
Key idea — the 100-hand threshold is a decision you must defend A player with 12 hands might show a VPIP of 100% purely by chance. That is noise, and K-Means will happily build a whole cluster out of it. Filtering to players with at least 100 hands makes the statistics meaningful — but it throws away real people, so you must report how many. In our sample file, most players appeared in fewer than 12 hands, because one file covers only ~2¼ minutes. Across the full 23 days the picture is completely different — which is exactly why you must run this on many files before judging the threshold.
Careful — the one line that will crash your laptop Never call .toPandas() or .collect() on joined, hp or the actions table. Those commands drag every row into the driver process, which on a laptop is the same 16 GB you are already using. It is the most common way students kill a local Spark job. Only call it on gold, which is one small row per player: pdf = gold.toPandas() is completely safe.
11 Step 7

Tuning for exactly 16 GB

SettingUseWhy for your machine
spark.driver.memory9gmacOS and your browser need the rest. Going higher causes swapping, which is slower than spilling.
master("local[N]")local[8]You have 4 performance + 6 efficiency cores. Leave two free or the machine becomes unusable while it runs.
spark.sql.shuffle.partitions48The default is 200, tuned for real clusters. On 8 local cores that is 200 tiny tasks and pure overhead. Roughly 4–6× your core count is a good starting point.
spark.local.dir/tmp/spark-scratchWhere Spark spills when RAM runs out. Your SSD is very fast, which is why 16 GB is workable at all.
spark.sql.files.maxPartitionBytes64mSmaller input partitions = less memory per task. Useful if you hit out-of-memory errors.
Takeaway — spilling is not failure When Spark says it is spilling to disk, that is the system working as designed, not breaking. It means a shuffle did not fit in RAM so it used the SSD instead. It gets slower; it does not get wrong. The only true failure is OutOfMemoryError in the driver, which almost always means you called .collect() on something huge.
12 Step 8

Handing off to Databricks

The guidelines require Databricks for Phases 2 and 3. You do not have to upload 18 GB to satisfy that.

  1. Do the heavy parsing locally on your Mac — Bronze to Silver. This is the slow, fiddly part and your machine is genuinely good at it.
  2. Upload the Silver Parquet (2–4 GB) or, if that is painful, just the Gold table (~200 MB). Both are small enough to move easily.
  3. Do Phase 2's final feature steps and all of Phase 3 on Databricks, in PySpark, so the graded notebook demonstrates exactly what the guidelines ask for.
  4. Also run the parser on a sample inside Databricks so the notebook shows the full pipeline end to end, even though the bulk ran locally.
  5. Document the split honestly in your report. Choosing where to run each stage is a real engineering decision, and explaining it is worth more than pretending everything ran in the cloud.
Careful — the platform changed this year Databricks Community Edition was retired on 1 January 2026. The replacement is Databricks Free Edition, which no longer needs an AWS or Azure account to sign up.
