This page is what gets written before any code runs — the exact target, the exact feature list, the model, and the honest risk for each fork — so whoever builds Fork A doesn't have to reverse-engineer the label from features.py, and the team can catch a leaky feature or an unfair baseline on paper instead of after training.

01 Shared foundation

The two Gold tables every fork reads

All three forks read from the same two tables — nobody touches Silver or Bronze again. That's the point of the medallion layout: 116.6M seat-rows in, a few hundred thousand rows out.

106,977
gold/player_features rows — one per (site, player), ≥100 hands. 41 cols, 18 MB.
21,556,288
gold/hand_features rows — one per hand. 20 cols, 389 MB.
61.8%
of the 280,363 players ever seen were dropped at the <100-hand filter — a floor, not a rounding error.
Where it breaks — player_features is a lifetime average, not a before/after split Every rate column in player_features — vpip, pfr, fold_rate, wtsd, aggression_factor, bb_per_100, hands_per_day, max_tables — is averaged over a player's entire recorded history, including whatever happened in the final week. features.py only splits activity counts into hands_prior / hands_final7; it does not compute a "rates up to the cutoff only" version of anything else. Consequence: any fork that predicts something about the future from past behaviour (Fork A's lapse label, Fork B's next-week-volume variant) is at risk of quietly training on data from inside the window it's trying to predict. This is the same class of bug the uncalled-bet fix and the pot_bb leakage guard in features.py already catch elsewhere in this project — it just hasn't been closed here yet. Each fork section below flags exactly where this bites and what the fix would cost.

03 Fork A
FORK A

Lapse classification

Flag players who are about to go quiet on a venue before their data simply stops — an early-warning list a retention team can act on, aimed at the recreational players who actually fund the rake.

Problem it solves

The operator earns rake only while people keep sitting down. Recreational players who quietly stop showing up are lost revenue that nobody notices until it's already gone. A model that scores currently active players by risk-of-lapsing turns "we lost some players last month" into "these 500 specific accounts are drifting — here's what a targeted offer to them is worth."

Honesty flag — this is lapse, not churn The dataset covers at most 26 days per venue. "Zero hands in the trailing week" is a short-horizon lapse signal, not proof anyone has permanently left. Say so every time this fork is presented — it's one of the named honesty rules for this project.

Target & label definition

Grounded in features.py's existing columns — no new Gold columns needed to build the label:

Groundedsrc/features.py — LAPSE_WINDOW, hands_final7, hands_prior, site_last_day

label = 1 if hands_final7 == 0 else 0, restricted to players with hands_prior > 0 (i.e. first_day <= site_last_day − 7) — a player who only shows up in the final week hasn't lapsed, they're new, and including them would mislabel arrivals as departures.

The trailing window is measured per venue, from that venue's own last observed day (ABS/PS day 20 · FTP day 23 · ONG day 24 · IPN/PTY day 26), not from a global calendar date — this is the fix for the bug that would otherwise label all of ABS and PS (44% of the dataset) as lapsed purely because their recording stops earlier.

Open decision — class balance is not yet measured Nobody has run value_counts() on this label yet. Do it before picking a metric or a class_weight setting — do not assume it's balanced, and do not guess a number for the report.

Feature set

Use as a featureExclude — leaks the label
vpip, pfr, fold_rate, wtsd, aggression_factor, vpip_pfr_gap, avg_invested_bb, avg_stack_bb, hands_per_day, max_tables / avg_tables / distinct_tables (null on iPoker — keep tables_recorded as a feature too), distinct_stakes, max_stake, btn_share, bb_vpip_rate, hands_prior (activity up to the cutoff — legitimate), a derived tenure_days = cutoff − first_day hands_final7, days_since_last, last_day — these are the label. site_last_day, raw first_day — contextual only, not features.

Every column in the left-hand list still carries the lifetime-aggregation caveat from the Shared section — they're not literally "known before the cutoff," they're "the best available proxy for it" until features.py is extended to compute prior-window-only rates.

Bake-off model — Step 5, a few hours

Baseline: majority-class predictor (predict "still active" for everyone). Candidate: a single interpretable model, chosen so a coefficient can go straight into the business narrative:

Score against the majority-class baseline with precision/recall/F1, not accuracy alone — a 93% accurate model that never flags anyone is worthless to a retention team.

04 Fork B
FORK B

Player value regression

Predict how much a player is worth going forward, so retention spend goes to high-value at-risk players first, not spread evenly across everyone.

Problem it solves

Not every lapsing player is worth the same retention effort. A model that ranks players by expected future value — money generated or volume of play — turns Fork A's "who's leaving" list into "who's leaving and worth calling about," which is the difference between a mass email and a targeted offer.

Two candidate targets, on the same table, with very different coverage:

Variant 1 — money value (rake-adjacent)

GroundedProject/CLAUDE.md — money-coverage measurement, 2026-08-07

Target: bb_per_100 (or avg_net_bb), computed only over money_hands — hands whose winnings actually reconcile against the pot.

Coverage by venue: ONG 99.1% · ABS 82.0% · PS 27.3% · FTP 27.2% · PTY 100% present but only 14% reconciling · IPN 0.0% — excluded entirely, it reconciles on none of its 6.0M hands. Overall, 88,655 of 106,977 kept players (82.9%) have any usable money at all; median money_hands is only 92.

Where it breaks — filter on money_hands, never hands_played 6.4% of players sit beyond ±200 bb/100 — not talent, a small-sample artifact from thin money coverage. Worst measured case: 103 hands played, 7 with usable money, −1,494 bb/100. Open decision: pick and record a minimum money_hands threshold (e.g. ≥30 or ≥50) before training — there is no verified "correct" number yet, this is a modelling call the team has to make and justify.

Variant 2 — next-week volume

Groundedsrc/features.py — hands_prior, hands_final7

Target: hands_final7 — hands played in the trailing 7 days before this venue's own last observed day. 100% coverage, no money-quality dependency.

Where it breaks — the same lifetime-aggregation leakage as Fork A Predicting hands_final7 from lifetime-averaged vpip/pfr/bb_per_100 etc. leaks final-week behaviour into the predictors, because those columns already include the final week in their average. The only cleanly "prior-only" feature currently in Gold is hands_prior itself. Closing this properly means extending features.py to compute rate columns restricted to day <= cutoff — an open feature-engineering task, not yet done.

Feature set (money variant — the cleaner of the two)

UseRole
money_handsfilter / confidence weight, not a predictor of value itself
vpip, pfr, aggression_factor, avg_stack_bb, max_tables, distinct_stakes, max_stake, site/venue predictors — this variant characterises realised value from contemporaneous behaviour, so lifetime aggregation is defensible here (it is not a forward-looking task unless explicitly reframed with a time split)

Baseline: mean predictor — per-venue mean, not a single global mean, given how much the venues differ in stakes and player mix. Candidate:

05 Fork C
FORK C

Hand economics regression

Predict pot size (in big blinds) from conditions known before a card is dealt — a proxy for revenue-per-seat: bigger pots mean more rake, so this says which tables, hours, and stakes generate the most rake per hand.

Problem it solves

Rake is a function of pot size. A model that predicts pot_bb from stake, seat count, time of day, and table depth tells an operator where to open more tables, staff support, or run promotions — which slices of the schedule are structurally worth more, before a single hand is dealt.

Honesty flag — frame this as revenue forecasting, not game analytics Without the business framing this reads as "predicting poker outcomes," which is the wrong story for a responsible-gaming-adjacent project. Every slide on this fork should open with the rake connection, not the poker mechanic.

Target & feature set — no leakage risk, exactly as coded

This is the cleanest fork methodologically: every hand is one row, and features.py already separates pre-hand from outcome columns explicitly.

Groundedsrc/features.py — gold/hand_features column groups

Target: pot_bb.

Features (known before a card is dealt): day, hour, minute_of_day, is_weekend, stake, big_blind, n_players, seat_count, avg_stack_bb, min_stack_bb, table_id / venue / site as categoricals.

Excluded — settled at the same time as the pot, target leakage: saw_flop, showdown, rake_bb, money_status. This exclusion is already written into features.py's column comments — do not add these back in.

Bake-off model — Step 5, a few hours

Baseline: mean pot_bb within each stake level — pot size scales with stake by construction, so a single global mean would make any real model look artificially good. Candidate:

Python — bake-off, local, scikit-learnfork c
# n_players x stake interactions are the expected nonlinear signal
from sklearn.ensemble import GradientBoostingRegressor
model = GradientBoostingRegressor(max_depth=4)
